# PLAN Skill 设计文档

> 公共计划生成能力 —— 供 task-split-skill 和 plan-review-skill 共用

---

## 1. 定位与职责

### 1.1 核心原则：复述 + 人工确认，人机确认最可靠

**所有关键信息必须经过「复述 + 用户确认」流程，LLM 自己理解的不算数。**

```
用户回答澄清问题
    ↓
LLM 复述理解
    ↓
用户确认 / 纠正
    ↓
才视为有效输入
```

**为什么这样做：**
- LLM 解析用户意图不可靠
- 用户一句话可能有多种理解
- 人机确认是确定性的保障
- 确认过的内容，出了问题用户自己负责（而不是 LLM 背锅）

**哪些环节必须确认：**

| 环节 | 确认内容 |
|------|---------|
| 项目愿景 | 目标描述是否准确 |
| MVP 范围 | 必须有的功能是否正确 |
| 里程碑 | 每个 milestone 的标题和验收标准 |
| 交付物 | 交付物名称和负责人 |
| 最终 PLAN | 整体内容是否正确 |

### 1.2 定位

PLAN skill 是**独立的 Skill**，不附属于 task-split 或 plan-review。

负责：
- 澄清用户需求
- 生成标准 `docs/PLAN.md`
- 校验 PLAN.md 格式

不负责：
- 评审（plan-review-skill 的职责）
- 拆解（task-split-skill 的职责）
- 追踪（target-skill 的职责）

### 1.2 核心能力

```
用户说「制定计划」/「写 PLAN」/「规划一下」
    ↓
PLAN skill 激活
    ↓
澄清问题 → 生成 PLAN.md → 格式校验
```

### 2.1 触发词

| 触发词 | 说明 |

| `制定计划` / `写 PLAN` / `创建计划` | 核心触发 |

| 不触发 | 原因 |

| `追踪目标` / `track goal` | → target-skill |

## 3. 标准 PLAN.md 格式

### 3.1 文件位置

`docs/PLAN.md`（固定路径，不可配置）

### 3.2 标准模板

```markdown
---
status: draft
version: 1.0
author: {user_name}
created: {YYYY-MM-DD}
updated: {YYYY-MM-DD}
---

# 项目愿景

<!-- 一句话描述项目核心目标 -->
<!-- 必须回答：做这件事要达到什么结果 -->

---

# 需求约束

## MVP（必须有的）

- <!-- 功能1 -->
- <!-- 功能2 -->

## 技术约束

- 技术栈：<!-- 如：FastAPI + PostgreSQL -->
- 运行环境：<!-- 如：Python 3.11+ -->

## 限制条件

- <!-- 预算/时间/兼容性等限制 -->

---

# 里程碑

<!-- 每个里程碑必须有明确的验收标准 -->

| ID | 里程碑 | 验收标准 | 状态 | 截止日期 |
|----|--------|---------|------|---------|
| M1 | <!-- 里程碑名称 --> | <!-- 可检查的验收条件 --> | pending | <!-- YYYY-MM-DD 或 空 --> |
| M2 | <!-- 里程碑名称 --> | <!-- 可检查的验收条件 --> | pending | <!-- YYYY-MM-DD 或 空 --> |

---

# 交付物

| 交付物 | 负责人 | 截止日期 | 关联里程碑 |
|--------|--------|---------|-----------|
| <!-- 交付物名称 --> | <!-- 负责人 --> | <!-- YYYY-MM-DD --> | M1 |
| <!-- 交付物名称 --> | <!-- 负责人 --> | <!-- YYYY-MM-DD --> | M2 |

---

# 风险预判

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| <!-- 风险描述 --> | 高/中/低 | 高/中/低 | <!-- 应对措施 --> |
```

### 3.3 必填字段

| 字段 | 位置 | 说明 |
|------|------|------|
| `# 项目愿景` | 必须 | 不能为空 |
| `| ID | 里程碑 |` 表格 | 必须 | 至少 1 个 milestone |
| 验收标准 | 里程碑表格列 | 不能写「待定」 |

### 3.4 格式校验规则

```
✅ 通过：愿景非空 + milestone 表格有内容 + 验收标准非「待定」
❌ 不通过：愿景为空 / milestone 表格为空 / 验收标准为「待定」
```

校验失败 → 提示用户修正，不生成文件。

## 4. 工作流程

### 4.1 完整流程

```
Step 1: 激活判断
    ↓ 检查是否已有 docs/PLAN.md
    ├── 已存在 → 询问「已存在，是否要重新创建？」
    └── 不存在 → Step 2

Step 2: 澄清问题
    ├── 用户已有明确想法 → 直接问关键字段
    └── 用户模糊 → 按模板引导

Step 3: 生成 PLAN.md
    ↓ LLM 填充模板
    输出 PLAN.md 内容
    ↓
Step 4: 格式校验
    ├── 通过 → 写入 docs/PLAN.md
    └── 不通过 → 提示用户修正

Step 5: 后续选项
    - 「评审计划」→ 触发 plan-review-skill
    - 「开始拆解」→ 触发 task-split-skill
    - 「先放着」→ 结束
```

### 4.2 澄清问题模板

```markdown
## 制定计划 - 澄清问题

在创建 PLAN.md 之前，请回答以下问题：

**1. 项目目标**
这个项目要实现什么？最终交付物是什么？
> {用户回答}

**2. MVP 范围**
必须有的功能有哪些？可以砍掉的有哪些？
> {用户回答}

**3. 技术约束**
有技术栈要求吗？运行环境限制？
> {用户回答}

**4. 里程碑（可选）**
有几个关键阶段？每个阶段的验收标准是什么？
> {用户回答}

**5. 时间约束（可选）**
有截止日期吗？
> {用户回答}
```

### 8.2 用户已有 PLAN.md 时的处理

```markdown
## ⚠️ 检测到已存在 PLAN 文件

**现有版本：**
| 文件 | 修改时间 | 状态 |
|------|---------|------|
| PLAN.md | 2026-05-15 | draft |
| PLAN-2026-05-10.md | 2026-05-10 | approved |

**选项：**
1. **覆盖 PLAN.md** — 更新当前主版本（历史保留）
2. **另存为 PLAN-2026-05-17.md** — 新建日期版本
3. **取消** — 不创建

请选择：
```

### 8.3 多版本处理规则

| 情况 | 处理方式 |
|------|---------|
| 只有 `PLAN.md` | 直接编辑（不另存） |
| `PLAN.md` + 历史版本 | 询问用户 |
| 多个历史版本，无 `PLAN.md` | 找最新的历史版本，询问是否升为主版本 |
| 用户指定文件名 | 按用户指定的生成 |

### 8.4 版本索引

每次生成或重大更新后，在文件末尾自动追加版本历史：

```markdown
---

## 版本历史

| 版本 | 日期 | 说明 |
|------|------|------|
| v1.0 | 2026-05-10 | 初始版本 |
| v1.1 | 2026-05-15 | 更新 MVP 范围 |
| current | 2026-05-17 | 当前版本 |
```

### 8.5 文件命名约定

```
docs/PLAN.md              # 始终是「当前主版本」
docs/PLAN-YYYY-MM-DD.md  # 历史版本存档（如 PLAN-2026-05-15.md）
docs/PLAN-v1.0.md        # 大版本存档
```

### 8.6 智能查找最新版本

当 task-split-skill 或 plan-review-skill 需要找 PLAN 时：

1. **优先 `docs/PLAN.md`**（当前主版本）
2. **如果没有，找最新的 `docs/PLAN-*.md`**
3. **找到后向用户确认**：是否使用这个版本？

## 5. 输出格式

### 5.1 标准输出

PLAN skill 执行完成后，输出：

```markdown
## ✅ PLAN.md 已生成

**文件位置**：`docs/PLAN.md`
**版本**：1.0
**状态**：draft

### 项目愿景
{项目愿景}

### 里程碑（{N} 个）
| ID | 里程碑 | 验收标准 |
|----|--------|---------|
| M1 | {标题} | {验收标准} |
| M2 | {标题} | {验收标准} |

### 下一步

1. **评审计划** — 触发 plan-review-skill 进行评审
2. **开始拆解** — 触发 task-split-skill 进行任务拆解
3. **修改计划** — 告诉我需要调整哪些部分
```

### 5.2 触发后续 skill 的方式

PLAN skill 不主动触发其他 skill，只输出建议选项，由用户决定是否继续。

## 6. 与其他 Skill 的联动

### 6.1 被调用关系

```
task-split-skill
└── 调用 PLAN skill（当用户需要先有计划）
plan-review-skill
└── 依赖 PLAN.md（假设已由 PLAN skill 生成）
```

### 6.2 文件契约

| 文件 | 创建者 | 消费者 |
|------|--------|--------|
| `docs/PLAN.md` | PLAN skill 或用户手动 | plan-review-skill, task-split-skill |

### 6.3 状态字段

PLAN.md frontmatter 的 `status` 字段：

| 状态 | 说明 | 谁设置 |
|------|------|--------|
| `draft` | 草稿，未评审 | PLAN skill 生成时 |
| `pending_review` | 待评审 | plan-review-skill 提交评审时 |
| `approved` | 已批准，可执行 | plan-review-skill 批准时 |
| `rejected` | 已驳回，需修订 | plan-review-skill 驳回时 |
| `obsolete` | 已废弃 | 用户手动 |

## 7. 边界定义

### 7.1 与 task-split-skill 的边界

| 场景 | 负责方 |
|------|--------|
| 用户说「制定计划」 | PLAN skill |
| 用户说「拆解任务」 | task-split-skill |
| 用户说「制定计划并拆解」 | PLAN skill → task-split-skill（分两步） |

### 7.2 与 plan-review-skill 的边界

| 场景 | 负责方 |
|------|--------|
| 生成 PLAN.md | PLAN skill |
| 评审 PLAN.md | plan-review-skill |
| 修改 PLAN.md（评审后） | PLAN skill（复用澄清流程） |

### 7.3 与 brainstorming skill 的边界

| 场景 | 负责方 |
|------|--------|
| 需求发散阶段 | brainstorming skill |
| 需求收敛后制定计划 | PLAN skill |

## 8. 错误处理

### 8.1 用户拒绝回答澄清问题

```
如果用户说「随便」/「你自己定」：

→ 使用合理默认值填充，标注「[待确认]」
→ 生成 PLAN.md 后明确提示用户哪些字段需要确认
```

### 8.2 用户已有 PLAN.md 但格式混乱

```
→ 尝试提取有效信息
→ 标注「[信息提取自现有 PLAN.md，部分字段需确认]」
→ 生成新 PLAN.md 前询问用户
```

### 8.3 校验失败

```
→ 明确告诉用户哪一行/哪一列格式错误
→ 提供修正建议
→ 不写入文件，等用户确认修正
```

## 11. 与 base-skill 的集成

### 11.1 安装方式

PLAN skill 是 base-skill 的标配 skill 之一。

在 base-skill 的 SKILL.md 中添加：

```markdown
## 标配 Skills

| Skill | 用途 |
|-------|------|
| task-split-skill | 任务拆解 |
| target-skill | 目标追踪 |
| plan-review-skill | 规划评审 |
| **PLAN skill** | **计划生成** |
```

### 11.2 触发优先级

当用户说「制定计划」时，PLAN skill 优先于其他 skill 响应。

### 11.3 base-skill 的 skill 组合

```
base-skill 标配 skill 组合：
├── task-split-skill（任务拆解）
├── target-skill（目标追踪）
├── plan-review-skill（规划评审）
└── PLAN skill（计划生成）
```

## 12. 多 Skill 联动机制

### 12.1 核心问题

当一个 skill 改了输出格式，其他 skill 可能不知道，导致不兼容。

### 12.2 解决方案：版本契约 + 变更通知

**版本契约文件**：`docs/schemas.md`

```markdown
# Schema 版本契约

## PLAN.md
- 版本：1.0
- 位置：`docs/PLAN.md`
- 消费者：plan-review-skill, task-split-skill

## .target-trigger
- 版本：1.0
- 位置：项目根目录
- 消费者：target-skill

## .target-state.json
- 版本：1.0
- 位置：项目根目录
- 消费者：target-skill

---

## 变更记录

| 日期 | Schema | 变更内容 | 影响范围 |
|------|--------|---------|---------|
| 2026-05-17 | .target-state.json | 新增 milestone + subTask 结构 | target-skill |
```

### 12.3 版本检查 SOP

当 skill 读取其他 skill 的输出时：

```markdown
## 检查版本

1. 读取输出文件的版本字段
2. 对比 `docs/schemas.md` 中的版本
3. 如果版本不匹配：
   → 提示用户：「版本不匹配，可能存在兼容性问题」
   → 不卡住，但明确告知
```

### 12.4 更新 skill 时的 SOP

```
1. 评估影响范围
   - 改了输出格式？→ 检查消费者
   - 改了输入格式？→ 检查提供者

2. 更新 docs/schemas.md
   - 追加变更记录
   - 更新版本号

3. 通知用户
   - 「此更新影响以下 Skill：xxx」
   - 「建议同步更新」

4. 在 skill 的 learns/ 记录
   - 本次变更对其他 skill 的影响
```

### 12.5 各 Skill 的版本字段

| 文件 | 版本字段 | 位置 |
|------|---------|------|
| `docs/PLAN.md` | `version` | frontmatter |
| `.target-trigger` | `version` | JSON 顶层 |
| `.target-state.json` | `schemaVersion` | JSON 顶层 |

## 13. 设计原则

1. **用户确认后才写入文件** — 所有必填字段必须经过用户确认
2. **格式校验是强制性的** — 校验不通过不写入文件
3. **不替用户做决定** — 里程碑、交付物等关键信息必须用户填
4. **中间产物必须留存** — PLAN.md 是中间产物，必须写入文件
5. **最小化依赖** — 不依赖任何外部 skill 或脚本，纯 LLM 驱动
6. **复述 + 确认** — LLM 理解后必须用户确认，才视为有效输入
