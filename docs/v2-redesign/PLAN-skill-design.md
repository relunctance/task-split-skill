# PLAN Skill 设计文档

> 公共计划生成能力 —— 供 task-split-skill 和 plan-review-skill 共用

---

## 1. 定位与职责

### 1.1 定位

PLAN skill 是**独立的 Skill**，不附属于 task-split 或 plan-review。

负责：
- 澄清用户需求
- 生成标准 `docs/PLAN.md`
- 校验 PLAN.md 格式

不负责：
- 评审（plan-review-skill 的职责）
- 拆解（task-split-skill 的职责）
- 追踪（target-skill 的职责）

### 1.2 核心能力

```
用户说「制定计划」/「写 PLAN」/「规划一下」
    ↓
PLAN skill 激活
    ↓
澄清问题 → 生成 PLAN.md → 格式校验
```

## 2. 触发条件

### 2.1 触发词

| 触发词 | 说明 |
|--------|------|
| `制定计划` / `写 PLAN` / `创建计划` | 核心触发 |
| `规划一下` / `帮我规划` | 自然语言 |
| `创建 PLAN.md` | 明确文件 |
| `project plan` / `make a plan` | 英文 |

### 2.2 不触发

| 不触发 | 原因 |
|--------|------|
| `评审计划` / `review PLAN` | → plan-review-skill |
| `拆解任务` / `task split` | → task-split-skill |
| `追踪目标` / `track goal` | → target-skill |

## 3. 标准 PLAN.md 格式

### 3.1 文件位置

`docs/PLAN.md`（固定路径，不可配置）

### 3.2 标准模板

```markdown
---
status: draft
version: 1.0
author: {user_name}
created: {YYYY-MM-DD}
updated: {YYYY-MM-DD}
---

# 项目愿景

<!-- 一句话描述项目核心目标 -->
<!-- 必须回答：做这件事要达到什么结果 -->

---

# 需求约束

## MVP（必须有的）

- <!-- 功能1 -->
- <!-- 功能2 -->

## 技术约束

- 技术栈：<!-- 如：FastAPI + PostgreSQL -->
- 运行环境：<!-- 如：Python 3.11+ -->

## 限制条件

- <!-- 预算/时间/兼容性等限制 -->

---

# 里程碑

<!-- 每个里程碑必须有明确的验收标准 -->

| ID | 里程碑 | 验收标准 | 状态 | 截止日期 |
|----|--------|---------|------|---------|
| M1 | <!-- 里程碑名称 --> | <!-- 可检查的验收条件 --> | pending | <!-- YYYY-MM-DD 或 空 --> |
| M2 | <!-- 里程碑名称 --> | <!-- 可检查的验收条件 --> | pending | <!-- YYYY-MM-DD 或 空 --> |

---

# 交付物

| 交付物 | 负责人 | 截止日期 | 关联里程碑 |
|--------|--------|---------|-----------|
| <!-- 交付物名称 --> | <!-- 负责人 --> | <!-- YYYY-MM-DD --> | M1 |
| <!-- 交付物名称 --> | <!-- 负责人 --> | <!-- YYYY-MM-DD --> | M2 |

---

# 风险预判

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| <!-- 风险描述 --> | 高/中/低 | 高/中/低 | <!-- 应对措施 --> |
```

### 3.3 必填字段

| 字段 | 位置 | 说明 |
|------|------|------|
| `# 项目愿景` | 必须 | 不能为空 |
| `| ID | 里程碑 |` 表格 | 必须 | 至少 1 个 milestone |
| 验收标准 | 里程碑表格列 | 不能写「待定」 |

### 3.4 格式校验规则

```
✅ 通过：愿景非空 + milestone 表格有内容 + 验收标准非「待定」
❌ 不通过：愿景为空 / milestone 表格为空 / 验收标准为「待定」
```

校验失败 → 提示用户修正，不生成文件。

## 4. 工作流程

### 4.1 完整流程

```
Step 1: 激活判断
    ↓ 检查是否已有 docs/PLAN.md
    ├── 已存在 → 询问「已存在，是否要重新创建？」
    └── 不存在 → Step 2

Step 2: 澄清问题
    ├── 用户已有明确想法 → 直接问关键字段
    └── 用户模糊 → 按模板引导

Step 3: 生成 PLAN.md
    ↓ LLM 填充模板
    输出 PLAN.md 内容
    ↓
Step 4: 格式校验
    ├── 通过 → 写入 docs/PLAN.md
    └── 不通过 → 提示用户修正

Step 5: 后续选项
    - 「评审计划」→ 触发 plan-review-skill
    - 「开始拆解」→ 触发 task-split-skill
    - 「先放着」→ 结束
```

### 4.2 澄清问题模板

```markdown
## 制定计划 - 澄清问题

在创建 PLAN.md 之前，请回答以下问题：

**1. 项目目标**
这个项目要实现什么？最终交付物是什么？
> {用户回答}

**2. MVP 范围**
必须有的功能有哪些？可以砍掉的有哪些？
> {用户回答}

**3. 技术约束**
有技术栈要求吗？运行环境限制？
> {用户回答}

**4. 里程碑（可选）**
有几个关键阶段？每个阶段的验收标准是什么？
> {用户回答}

**5. 时间约束（可选）**
有截止日期吗？
> {用户回答}
```

### 4.3 已存在时的处理

```markdown
## ⚠️ PLAN.md 已存在

检测到项目根目录已存在 `docs/PLAN.md`。

**当前计划**：
- 目标：{目标描述}
- 里程碑：{N} 个
- 状态：{status}

**选项**：
1. **重新创建** — 覆盖现有 PLAN.md（会丢失评审记录）
2. **查看现有** — 显示现有内容
3. **取消** — 不做修改

请选择，或告诉我您的决定。
```

## 5. 输出格式

### 5.1 标准输出

PLAN skill 执行完成后，输出：

```markdown
## ✅ PLAN.md 已生成

**文件位置**：`docs/PLAN.md`
**版本**：1.0
**状态**：draft

### 项目愿景
{项目愿景}

### 里程碑（{N} 个）
| ID | 里程碑 | 验收标准 |
|----|--------|---------|
| M1 | {标题} | {验收标准} |
| M2 | {标题} | {验收标准} |

### 下一步

1. **评审计划** — 触发 plan-review-skill 进行评审
2. **开始拆解** — 触发 task-split-skill 进行任务拆解
3. **修改计划** — 告诉我需要调整哪些部分
```

### 5.2 触发后续 skill 的方式

PLAN skill 不主动触发其他 skill，只输出建议选项，由用户决定是否继续。

## 6. 与其他 Skill 的联动

### 6.1 被调用关系

```
task-split-skill
└── 调用 PLAN skill（当用户需要先有计划）
plan-review-skill
└── 依赖 PLAN.md（假设已由 PLAN skill 生成）
```

### 6.2 文件契约

| 文件 | 创建者 | 消费者 |
|------|--------|--------|
| `docs/PLAN.md` | PLAN skill 或用户手动 | plan-review-skill, task-split-skill |

### 6.3 状态字段

PLAN.md frontmatter 的 `status` 字段：

| 状态 | 说明 | 谁设置 |
|------|------|--------|
| `draft` | 草稿，未评审 | PLAN skill 生成时 |
| `pending_review` | 待评审 | plan-review-skill 提交评审时 |
| `approved` | 已批准，可执行 | plan-review-skill 批准时 |
| `rejected` | 已驳回，需修订 | plan-review-skill 驳回时 |
| `obsolete` | 已废弃 | 用户手动 |

## 7. 边界定义

### 7.1 与 task-split-skill 的边界

| 场景 | 负责方 |
|------|--------|
| 用户说「制定计划」 | PLAN skill |
| 用户说「拆解任务」 | task-split-skill |
| 用户说「制定计划并拆解」 | PLAN skill → task-split-skill（分两步） |

### 7.2 与 plan-review-skill 的边界

| 场景 | 负责方 |
|------|--------|
| 生成 PLAN.md | PLAN skill |
| 评审 PLAN.md | plan-review-skill |
| 修改 PLAN.md（评审后） | PLAN skill（复用澄清流程） |

### 7.3 与 brainstorming skill 的边界

| 场景 | 负责方 |
|------|--------|
| 需求发散阶段 | brainstorming skill |
| 需求收敛后制定计划 | PLAN skill |

## 8. 错误处理

### 8.1 用户拒绝回答澄清问题

```
如果用户说「随便」/「你自己定」：

→ 使用合理默认值填充，标注「[待确认]」
→ 生成 PLAN.md 后明确提示用户哪些字段需要确认
```

### 8.2 用户已有 PLAN.md 但格式混乱

```
→ 尝试提取有效信息
→ 标注「[信息提取自现有 PLAN.md，部分字段需确认]」
→ 生成新 PLAN.md 前询问用户
```

### 8.3 校验失败

```
→ 明确告诉用户哪一行/哪一列格式错误
→ 提供修正建议
→ 不写入文件，等用户确认修正
```

## 10. 设计原则

1. **用户确认后才写入文件** — 所有必填字段必须经过用户确认
2. **格式校验是强制性的** — 校验不通过不写入文件
3. **不替用户做决定** — 里程碑、交付物等关键信息必须用户填
4. **中间产物必须留存** — PLAN.md 是中间产物，必须写入文件
5. **最小化依赖** — 不依赖任何外部 skill 或脚本，纯 LLM 驱动
