# 锚点方案设计

> 沉淀时间：2026-05-17
> 状态：方案已确认，待实施

---

## 一、问题背景

expert-teams 的 `task/PLAN.md` 共 3716 行，包含 M1~M5 的完整规划。

用户痛点：
- 想评审 M1-3，但 skill 只能评审整个文件
- 想拆解 M2，但 skill 只能拆解整个文件
- M2/M3/M4/M5 太远，不应该和 M1 混在一起评审/拆解

---

## 二、锚点方案

### 核心思路

保持单一文件，通过「锚点」定位局部内容。

```
用户：评审 M1-3
    ↓
plan-review-skill 识别「M1-3」锚点
    ↓
定位 PLAN.md 中 M1/M2/M3 相关区域
    ↓
局部评审
    ↓
输出修改建议（不直接修改）
```

---

## 三、锚点类型设计

| 锚点格式 | 含义 | 示例 |
|---------|------|------|
| `M1` | 单个里程碑 | 评审 M1 |
| `M1-3` | 范围里程碑 | 评审 M1+M2+M3 |
| `#架构` | 章节锚点 | 评审「架构」章节 |
| `表:交付物` | 表格锚点 | 评审「交付物」表格 |
| `L100-L200` | 行号锚点 | 评审指定行范围（专家用） |

## 四、plan-review-skill 改动

### 4.1 新增章节：锚点评审 SOP

```markdown
## 锚点评审（扩展能力）

### 锚点识别流程

```
1. 解析用户输入中的锚点
   - M1-3 → milestones 表格行
   - #架构 → 章节标题
   - 表:交付物 → 表格标题
2. 在 PLAN.md 中定位锚点对应区域
3. 裁剪出局部内容
4. 对局部内容执行评审
5. 输出修改建议（含原文位置）
```

### 锚点识别示例

```
用户：评审 M1-3

识别锚点：M1, M2, M3
    ↓
定位 milestones 表格中的 M1/M2/M3 行
    ↓
提取每个里程碑的：
  - 标题
  - 内容描述
  - 验收标准
  - 截止日期
    ↓
对每个里程碑执行评审检查清单
    ↓
输出 M1-3 的评审结果
```

### 4.2 新增输出格式

|--------|------|------|

## 五、task-split-skill 改动

### 5.1 Step 0.5 新增：锚点识别

```markdown
### Step 0.5：锚点识别（可选）

如果用户指定了锚点（如「拆解 M2」），先识别锚点：

```
1. 解析锚点：M2 / M1-3 / #架构 等
2. 定位锚点区域：
   - M2 → 找 milestones 表格 M2 行
   - 提取 M2 的：验收标准、交付物、截止日期
3. 确定拆解范围：只拆锚点覆盖的内容
4. 在输出中标记「来源锚点：M2」
```

**锚点解析规则**：
- `M1` → milestones 表格第 N 行
- `M1-3` → M1 + M2 + M3 行的验收标准
- `#架构` → `## 架构` 章节内容
```

### 5.2 输出标记来源锚点

```markdown
## 拆解结果（局部锚点）

> **来源锚点**：M2
> **覆盖范围**：M2 验收标准 + 交付物

### milestone: M2

| subTask ID | 任务 | 验收标准 | 预估时间 |
|------------|------|---------|---------|
| M2-1 | 实现 team create | `team create --id test --flow dev` 返回成功 | 15min |
| M2-2 | 实现 flow advance | `flow advance test` 状态推进 | 20min |
```

## 八、设计原则

1. **代码：0 行**。全部用 SOP + LLM
2. **Skill 是文档驱动**。Skill 的能力由 SKILL.md 定义，不写代码
3. **用户控制**。输出修改建议，用户确认后才生效
4. **可叠加**。可以多次评审/拆解不同锚点，不互相覆盖
